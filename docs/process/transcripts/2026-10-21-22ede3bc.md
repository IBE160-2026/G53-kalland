**Why it's a risk** (from `docs/process/vurderingskriterier.en.md`):

1. **The examiner looks at one commit.** "The examiner clones the repo and checks out the **last commit before the deadline** … reads the history, process documents and code." That commit is on `main`. If `docs/process/` is gitignored there, the checkout has no process documents. A clone does fetch the `process` branch, but the examiner would have to know to look for it and check it out separately.

2. **This puts 30 % at stake.** Process and AI governance is the biggest criterion. An A–B needs "prompts and decisions are linked to concrete changes", and C is "the link to code is partly implicit". On an orphan branch with no shared history, every link between logs and code becomes a GitHub URL across branches. Nothing in a code commit or file tree points back to its log. That pushes you toward the "partly implicit" description, and it's close to the warning sign "AI documentation that is generic and cannot be linked to concrete changes."

3. **README and tidiness (15 %).** The README must link to the process documentation. A link to another branch works on GitHub, but not for someone reading the checked-out commit locally.

4. **History can't be kept cheaply.** An orphan branch starts with no history. Keeping the existing log history would mean rewriting it (e.g. `git filter-repo` or `git subtree split`), not just copying files. Without that, the process branch looks like it was created all at once, which is close to another warning sign: "planning documents … clearly written afterwards."

Nothing in the teacher's feedback addresses this, so it doesn't change the picture.

**Your goal ("never committed together with code") is reachable without leaving `main`.** Process files could go only through their own `docs/` commits and PRs. Code branches would never touch `docs/process/`, and code PRs would link to the session log and the D-xxx decisions.
