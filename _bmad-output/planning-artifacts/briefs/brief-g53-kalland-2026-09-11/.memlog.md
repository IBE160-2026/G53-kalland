topic: Modular DAM/CRM platform for a design agency
updated: 2026-09-11T15:18
---

- (decision) Real-world tool: built first for Marthe's own design agency, with intent to offer to other agencies later (eventual multi-tenant SaaS is a genuine roadmap goal, not just a course narrative beat).
- (event) Solo group member (IBE160), deadline December 2026 — scopes brief/PRD rigor to what one person can realistically build and defend by then.
- (decision) V1 test scale: ~500 images, ~10 customers. Real-world eventual scale: thousands of images, hundreds of clients — architecture should not block that growth but v1 build/testing targets the smaller numbers.
- (assumption) No hard numbers on current time lost searching for images; framed qualitatively in the brief rather than with a specific metric.
- (decision) Tech stack is free choice; course (IBE160) primarily teaches JavaScript/TypeScript and Python, so stack will likely draw from those ecosystems, decided later at architecture stage.
- (decision) V1 scope: Tripletex integration and the Norwegian language pack are deferred past December — English-only, manual/internal purchase logging for v1. Both are explicit fast-follows, so the architecture (billing/invoicing hooks, i18n string externalization) must be designed to make adding them later straightforward rather than a rework.
- (decision) User chose coaching path over the suggested fast path — working section by section with real pushback rather than batching questions and drafting with [ASSUMPTION] tags.
- (decision) Access/pricing model per image, confirmed: (1) Internal-only — not visible to any customer; (2) Owned/free — tied to one specific customer (already theirs, no charge); (3) Stock-pool — visible either to all customers (public) or a restricted customer list, and priced either free-for-everyone or one-time purchase (buy-and-keep, per earlier Option A decision).
- (decision) V1 asset scope: images only. Video is the clear next asset type post-v1, explicitly deferred — noted that video will need a different AI metadata-generation approach (transcription/frame analysis vs. single-image vision model), so the asset-ingestion pipeline should be designed with that extension point in mind rather than hard-coded to images.
- (override) Corrected the 3-tier access model (internal/owned-free/stock-pool) — user pointed out owned/free and restricted-stock-pool overlap. Replaced with two independent attributes per image: visibility (public / restricted-to-customer-list / internal-only-i.e.-empty-list) and price (free / one-time paid). 'Owned/free' is just restricted-to-one-customer + free; no separate category needed.
- (decision) V1 roles: single internal 'admin' role covers all agency staff (upload, manage access, pricing). Data model should not hard-code single-role assumptions, so additional internal roles (e.g. regular staff vs admin) can be added later without a rework.
- (decision) Search for v1: keyword/metadata search only (over AI-generated + manual metadata). AI visual-similarity search explicitly deferred, not needed for v1.
- (decision) Working name: 'CRM-DAM' (placeholder/working name, not final branding).
- (decision) Duplicate detection: catch duplicate uploads using both file hashing (exact/near-duplicate content match) and filename matching.
- (decision) Versioning: staff can upload a new version of an existing asset (replacing/updating it in place) rather than only creating unrelated new records — asset identity persists across versions.
- (decision) Non-functional requirement: the system needs regular backups of the entire system (asset files + database), given it holds customer-licensed images and billing-relevant purchase logs for a real agency.
