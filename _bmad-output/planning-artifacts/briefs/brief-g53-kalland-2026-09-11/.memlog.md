- (decision) Real-world tool: built first for Marthe's own design agency, with intent to offer to other agencies later (eventual multi-tenant SaaS is a genuine roadmap goal, not just a course narrative beat).
- (event) Solo group member (IBE160), deadline December 2026 — scopes brief/PRD rigor to what one person can realistically build and defend by then.
- (decision) V1 test scale: ~500 images, ~10 customers. Real-world eventual scale: thousands of images, hundreds of clients — architecture should not block that growth but v1 build/testing targets the smaller numbers.
- (assumption) No hard numbers on current time lost searching for images; framed qualitatively in the brief rather than with a specific metric.
- (decision) Tech stack is free choice; course (IBE160) primarily teaches JavaScript/TypeScript and Python, so stack will likely draw from those ecosystems, decided later at architecture stage.
- (decision) V1 scope: Tripletex integration and the Norwegian language pack are deferred past December — English-only, manual/internal purchase logging for v1. Both are explicit fast-follows, so the architecture (billing/invoicing hooks, i18n string externalization) must be designed to make adding them later straightforward rather than a rework.
- (decision) User chose coaching path over the suggested fast path — working section by section with real pushback rather than batching questions and drafting with [ASSUMPTION] tags.
- (decision) Access/pricing model per image, confirmed: (1) Internal-only — not visible to any customer; (2) Owned/free — tied to one specific customer (already theirs, no charge); (3) Stock-pool — visible either to all customers (public) or a restricted customer list, and priced either free-for-everyone or one-time purchase (buy-and-keep, per earlier Option A decision).
- (decision) V1 asset scope: images only. Video is the clear next asset type post-v1, explicitly deferred — noted that video will need a different AI metadata-generation approach (transcription/frame analysis vs. single-image vision model), so the asset-ingestion pipeline should be designed with that extension point in mind rather than hard-coded to images.
- (override) Corrected the 3-tier access model (internal/owned-free/stock-pool) — user pointed out owned/free and restricted-stock-pool overlap. Replaced with two independent attributes per image: visibility (public / restricted-to-customer-list / internal-only-i.e.-empty-list) and price (free / one-time paid). 'Owned/free' is just restricted-to-one-customer + free; no separate category needed.
- (decision) V1 roles: single internal 'admin' role covers all agency staff (upload, manage access, pricing). Data model should not hard-code single-role assumptions, so additional internal roles (e.g. regular staff vs admin) can be added later without a rework.
- (decision) Search for v1: keyword/metadata search only (over AI-generated + manual metadata). AI visual-similarity search explicitly deferred, not needed for v1.
- (decision) Working name: 'CRM-DAM' (placeholder/working name, not final branding).
- (decision) Duplicate detection: catch duplicate uploads using both file hashing (exact/near-duplicate content match) and filename matching.
- (decision) Versioning: staff can upload a new version of an existing asset (replacing/updating it in place) rather than only creating unrelated new records — asset identity persists across versions.
- (decision) Non-functional requirement: the system needs regular backups of the entire system (asset files + database), given it holds customer-licensed images and billing-relevant purchase logs for a real agency.
- (event) Update run started 2026-10-16: reconcile brief with teacher feedback (tilbakemelding-product-brief.en.md, 2026-10-06). Tracked in issue #7; resolves open decision D-006 (V1 scope).
- (decision) User chose coaching path for the update and agrees with the teacher that v1 should be narrowed to the core flow (upload -> AI metadata -> visibility x price -> client views/downloads/buys -> purchase logged). Item-by-item placement still to confirm.
- (override) Reframed v1: v1 (Dec 2026) is the IBE160 course deliverable running on sample data, not the agency's production rollout; agency use comes after stage-2 work. Backup moved from v1 NFR to stage 2 (overrides 2026-09-11 backup decision) because v1 holds no real agency data. User wants v2 features planned now so implementing them later avoids big rewrites.
- (decision) UI language: English is the base language of the app (v1); Norwegian is a language pack added on top later. UI strings externalized from day one. Consistent with D-008 (Norwegian pack is product content).
- (decision) v2 accommodation rule: a deferred feature gets a v1 accommodation only if it is a field, relation, or convention that is free at start and expensive to retrofit; never a feature or abstraction layer. Accepted accommodations: asset/file-version split, purchase price snapshot, tenant_id on top-level tables (no scoping layer), externalized UI strings, media-type field + swappable AI provider, role field. 'Extended without rewrite' becomes a design constraint, not a success criterion.
- (decision) Versioning: data model accommodates it in v1 (asset vs file version); the versioning feature itself (upload new version, UI) is a stretch goal, built only if the core flow is done and stable.
- (decision) Metadata: on upload, extract all embedded metadata from the file (EXIF/IPTC/XMP) in addition to AI-generated title/description/alt-text/keywords; all metadata fields are manually editable by staff.
- (event) User proposed three AI provider families: cloud (start Gemini Flash, user supplies own API key; more cloud providers later), CLI (start Claude CLI; Codex/Gemini CLI later), local (start Gemma 4 12B via Ollama, also as fallback). Verified: Gemma 4 12B exists with image input and is on Ollama; Gemini Flash has a free tier (free-tier data may be used by Google). Placement in v1 vs stage 2 under discussion.
- (decision) CLI provider rationale: the agency already has Claude Code and Codex subscriptions, so a CLI provider is the cheapest way for the agency to use and test the app.
- (decision) GPS from EXIF is kept and stored; a map view to find images by location is a later-version feature (stage 2). Metadata may be wrong on upload, so edits must be reflected in the image file itself, not only in the app's record.
- (decision) Metadata write strategy: write on export. Stored original file stays unchanged (stable hash for duplicate detection, clean versions); database is source of truth for metadata; current metadata is written into the copy at download. Chosen over write-on-edit, which would break hash-based duplicate detection and blur versioning.
- (decision) GPS is stripped from files downloaded by clients; kept internally for the agency (and the later map view).
- (decision) AI providers v1: provider interface + mock provider (tests, examiner, no key) + Claude CLI as the one real provider. Stage 2: Codex/Gemini CLI, cloud API providers (Gemini Flash first, user-supplied key), local Ollama (Gemma 4 12B). Fallback in v1 is manual editing, not a provider chain.
- (decision) Tenant branding (agency logo/colors) moved to stage 2, alongside per-client branding.
- (override) Filename matching downgraded from duplicate-detection check to warning only (overrides 2026-09-11 decision): with exact hashing it only flags different files sharing a name, so it must never reject an upload.
- (event) User drafted success criteria: identical uploads rejected; images viewed only by those with access; end-to-end flow; clients fetch images independently. Being sharpened into checkable form.
- (decision) Success criteria replaced with 7 checkable ones: access matrix (visibility x price, automated), duplicates (identical rejected, same-name warned), end-to-end flow runnable in mock mode from README with seeded users + freely licensed sample images, client self-serve, purchase log (price snapshot, visible both sides), correct files out (edited metadata, no GPS), AI failure does not block upload. Removed: 'meaningfully faster', 'defensible as IBE160 deliverable', 'extended without rewrite' (now a design constraint).
- (decision) Paid images: clients see a small preview without watermark before purchase; the original is downloadable only after purchase.
