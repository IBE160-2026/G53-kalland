#### Would switching to Better Auth later be hard?

**Not if we draw one boundary now. Very hard if we don't.**

- **Easy version: everything goes through one auth module.** Pages, actions and route handlers only call a few functions, such as `getSession()`, `requireStaff()`, `requireContact()`, `login()`, `logout()`, `createSetupLink()` and `useSetupLink()`. A switch to Better Auth then changes:

  - **the user and session tables:** a migration that moves password hashes to Better Auth's table layout. Better Auth can be configured to verify existing argon2 hashes, so nobody has to reset their password
  - **one forced log-out** when you switch, which is harmless
  
  Roughly half a day to a day, and the access-rule tests prove nothing broke.
- **Hard version: session checks are scattered.** If pages read cookies and query the sessions table themselves, a switch means hunting through the whole app.

So the spine gets a rule: **only the auth module touches sessions, cookies and password hashes.** That rule also keeps the session handling consistent across stories, even if we never switch.

```
src/db/              Drizzle schema + migrations
worker/              the background process (same code, same image)
```

The rules that would come with it:
1. **Routes call modules, and only modules touch the database.** No Drizzle queries in pages.
2. **A module's public face is its `index.ts`.** Other modules import from there and never from inside another module.
3. **One owner per table.** For example, only `licences` writes licences, and only `images` changes an image's status.
4. **`access` decides everything a client may see, download or buy** (NFR-2a). Other modules ask it; none re-implement the rules.
5. **Reads happen in Server Components, and form changes go through Server Actions.** Server Actions get Next.js's built-in check that the request comes from your own site, which is the CSRF protection. **File traffic (upload, download, preview) goes through Route Handlers**, because those are byte streams. Every Route Handler that changes state checks the request's origin itself.

The alternative is organising by technical layer (`components/`, `services/`, `repositories/`). It's familiar, but it spreads one feature across many folders, which makes stories harder to keep separate and traceable.

## Claude · 14:03:18

Close, but not quite. The terms overlap, and in this project "vertical slice" is used in three different ways, so it's worth separating them.

#### Three meanings

**1. Vertical slices as code structure (by use case).** Each *use case* gets a folder holding everything it needs: UI, handler, validation and data access. For example, `features/checkout/`, `features/upload-image/`, `features/revoke-licence/`. Slices share as little as possible, and duplication is accepted to keep them independent.

**2. Modular monolith (by domain).** Each *domain* gets a module that owns its data and rules and exposes a public interface. For example, `modules/licences/`, `modules/images/`, `modules/access/`. A use case such as checkout *calls* several modules: access, licences and images.

**3. Vertical slice as delivery (build order).** This is what the PRD means by *"the first stories build a thin slice through the whole spine"*: each story delivers something working from UI to database. It's about *how you build*, not *how the code is organised*.

#### How they differ in this app

The difference shows in the **shared rules**. The access table (A1–A13) applies in search, the image page, previews, downloads, the cart and checkout, which is six use cases.

- **With use-case slices (1)**, each slice would either repeat the access rule or reach into a shared folder. Repeating it is exactly what NFR-2a forbids ("one access module"). A shared folder is a domain module under another name.
- **With domain modules (2)**, `access` owns the rule once, and every use case asks it. The same goes for licences (S5: one active licence) and the file pipeline (FR-35/36: no location data out).

The app is small, but it has a few **hard rules that many features share**. That's the case where domain modules beat use-case slices.

#### A note on the teacher's example

`technology.md` calls its modules "vertical slices" (`identity`, `commerce`, `catalog` …), but those are really **domain modules**: meaning 2 under meaning 1's name. So in the teacher's vocabulary, what I'm proposing is the same thing.

#### What I'd write in the spine

> **Modular monolith:** code is organised in domain modules that own their data and rules; **stories are delivered as vertical slices** that cut through routes and the modules they need.

The code structure is domain modules, and each story is a thin, working slice through them.
