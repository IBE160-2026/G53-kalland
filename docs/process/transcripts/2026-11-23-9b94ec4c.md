## Claude · 07:37:48

Both decisions are now in the run's working log. Next topic: **the image lifecycle and background generation**.

From the PRD, an image has two kinds of state that change independently:
- **Publication status:** draft → published → archived, and back from archived (FR-19a, FR-26). A published image never returns to draft. A never-published draft can be discarded (FR-20).
- **Processing state:** uploading, queued, generating, ready, failed or rejected (FR-15). Rules link the two: publishing is blocked while an image is queued or generating, and retrying works on drafts only.

FR-15 (background generation) is a bonus at rank 10. Without it, images are processed while the upload page waits. So the design has to work both ways without being built twice.

Here is how I'm leaning on each part, and the alternatives I weighed:

**1. Two separate state fields, both owned by the images module.**
`status` and `processingState` are separate columns, and only the images module changes them, through named actions (`publish`, `archive`, `claimNextQueued`, `markGenerated`, `markFailed`, `retry`). Each action checks the rules above. The alternative is one combined state like "draft-generating", which multiplies into about 12 combinations. Separate fields are simpler.

**2. "Uploading" and "rejected" exist only in the browser.**
The server creates the image record only after the whole file is stored and its fingerprint (hash) checked. A duplicate is rejected before any record exists (FR-10a). That way a server restart can never leave half-uploaded records behind. The server only knows **queued, generating, ready and failed**, which makes "after a restart, every image ends as ready or failed" easy: on startup, anything still `generating` goes back to `queued`.

**3. The image table is the job queue. No queue library.**
- **pg-boss or graphile-worker:** well tested, but they keep their own job table next to the image's processing state. Two records of "is this image being worked on?" can drift apart.
- **Own queue on the image table:** the worker picks the next `queued` image with `FOR UPDATE SKIP LOCKED`, a Postgres feature that lets several workers take different rows safely, and marks it `generating`. That's about 50 lines, with one source of truth, and a natural fit for Drizzle. **This is what I'd pick.**

**4. One function, two callers.**
`generateMetadata(imageId)` does the work: resize, call the AI provider, check the output, save. Without FR-15, the upload route calls it directly. With FR-15, a separate worker process calls it. The worker runs from the same Docker image as the app, with a different start command, as its own Compose service. So FR-15 is mostly "add the worker loop", not a rewrite.

**5. Status updates on screen: polling.**
The upload page asks every ~3 seconds for the states of the batch's images. That meets "within 10 seconds without a reload" (AS-23). Live push from the server (server-sent events or WebSockets) is more machinery than this needs.

How does this match how you picture the upload flow? I'm least sure about point 2. Does "uploading" being browser-only fit what you designed in the UX prototype, or does the review screen show server-side images still arriving, for example to another staff member looking at the same batch?
