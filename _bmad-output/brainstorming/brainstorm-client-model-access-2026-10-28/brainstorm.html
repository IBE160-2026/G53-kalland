Edge tests on top of the table: S1 deactivated contact → rejected on the next request · S2 deactivated org → all its contacts rejected · S3 archived asset → still in "Mine bilder" for buyers, gone from Butikk · S4 restricted with an empty list = internal-only · S5 two simultaneous purchases → one row · S6 every admin route with a client session → 403 · S7 buying a free asset → refused · S8 setup link reused or expired → refused · S9 deactivating the last admin → refused · S10 deleting an org that has purchases → refused.

🔐 The five rules that emerged

  1. The org holds the key; the person turns it.The organisation is the unit of access, ownership and history. The user is the unit of login and audit.
  2. There are two kinds of key.A visibility grant is free and follows the current visibility. A purchase grant is permanent: it survives changes to visibility and price, archiving, and the buyer leaving.
  3. Nothing with history is ever deleted.Assets and orgs that have purchases are archived or deactivated, never hard-deleted. This one rule settles most of the edge cases.
  4. Login doesn't need email.Admins issue single-use setup links. In stage 2 the same token is simply sent by email, so nothing needs rebuilding.
  5. All access checks go through one place.canSee, canDownloadOriginal and canBuy live in one module, matching the truth table above row by row. That gives a traceable line from plan to code to test.
